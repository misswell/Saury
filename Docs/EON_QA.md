### 场景 01 · 即将扣费卡片甩动（§8.1）

同一支脚本：四枪，慢拖 → 向右甩 → 向左甩 → 大力甩，每枪之间只歇 90 ms（短于一轮定位）。

| | 基准 021d939 | 现在 |
| --- | --- | --- |
| 拖 −150 pt 时轨道位置 | **−0.217 页**（逆着手指） | **+0.621 页** |
| 每 pt 换多少页 | 0.00414（但符号反了） | 0.00414（`1.35 / 326`，幅度一字未改） |
| 松手那一帧，屏幕离目标还差 | 1.217 / 1.283 / 1.348 / 1.413 页 | 0.379 / 0.083 / 1.006 / 0.446 页 |
| 松手→首帧动 | +46 / +1 / +32 / +4 ms | +17 / +20 / +10 / +20 ms |
| 松手到停 | 1067 / 868 / 602 / 387 ms（64 / 52 / 37 / 24 帧） | 888 / 640 / 408 / 157 ms（48 / 34 / 24 / 10 帧） |
| 窗口内最低彩色占比 | 535‰ | 841‰ / 870‰ |
| 近全黑帧 | 0 | 0 |

三条要说明的：

1. **符号**：`cardLayer` 两边逐字相同（`depth = index − position`，`depth<0` 那一支按
   `depth × width × 0.92` 往左飞出屏）。所以向左拖**必须**让 `position` 变大才对，
   基准写的是 `position = focused + translation/width × 1.35`，符号是反的 ——
   向左拖 150 pt 时卡片 0 的 `depth` 变成 +0.217，走的是「退到后面」那一支，只挪 3 px。
   这就是 §8.1 说的「容易造成跨索引边界的跳变」的真相：不是跳变引起的手感差，
   是**方向反了导致拖动看起来没反应**。
2. **单帧瞬移**（§12.2「动画结束后是否出现位置修正或跳动」）：基准日志
   `x=121.9 position=1.505 focused=1` → 下一帧 18 ms 后 `x=146.2 position=2.212 focused=2`。
   手指只走了 24.3 pt（该走 0.101 页），`position` 却跳了 **+0.707 页**；
   按 `cardLayer` 换算，焦点卡从 −152 px 一步到 −365 px，**单帧 213 px**。
   成因就是基准把每一帧的基准点挂在会跳的 `focused` 上。现在 `anchor` 在起手那一帧钉死，
   同一次拖动的每帧步进恒为 0.101 页，没有这一跳。
3. 那 1.006 页不是补跳：第三枪 `predicted` 换算过来正好指向第 2 页，是甩动速度该走的路。
   「松手才跳」和「手指没走完」是两件事，前者基准四枪全有（1.2–1.4 页），现在一枪都没有。

### 场景 03 · 周期切换与数字竞争（§9.3）

同一份剧本：两次快接一次慢接，再来一组 120 ms 四连点。

基准的日志把竞争写得很清楚（`before/03-period-number.log`）：

```
10:21:07.144  第2轮收尾回调 当前第3轮 屏幕上=361.22 真值=681.36 还在动=true
10:21:09.128  第4轮收尾回调 当前第7轮 屏幕上=254.91 真值=681.36 还在动=true
10:21:09.385  第6轮收尾回调 当前第7轮 屏幕上=227.12 真值=681.36 还在动=false
```

最后那一行是洞本身：第 7 轮正在往 **227.12** 走，第 6 轮的 `asyncAfter` 却报「真值=681.36、
还在动=false」。看基准的实现就知道这一行落下时屏幕会干什么：那个闭包打完日志之后无条件
`running = false`（pristine `021d939` 的 `Saury/Views/Components/Motion.swift:109-111`，
`git show 021d939:Saury/Views/Components/Motion.swift` 可查；那份带探针的副本把行号往后挪了
几行，量测时看到的是 `:131-132`），而
`Text(format(running ? current : target))`（同一文件 `:87`）一读到 `running=false`
就直接换成 `target` —— 而这个 `target` 是活的 `@State`，是**当下那一轮**的终点。
所以每一句「上一轮的收尾回调」都是屏幕上的一次**一步跳到位**。最清楚的是第 2 轮那一句：

```
10:21:06.988  起第3轮 从680.81 到 227.12
10:21:07.144  第2轮收尾回调 当前第3轮 屏幕上=361.22 真值=681.36 还在动=true
10:21:07.637  第3轮收尾回调 当前第3轮 屏幕上=227.12 真值=227.12 还在动=false
```

中间那一行落下时屏幕正在 361.22 上滚，`running` 被置 false → 一步跳到终点 227.12
（**单帧 −134.10**），比这一轮自己那行落定（07.637）早 0.49 秒，比 0.62 s 的常量早 0.46 秒，
时间轴同时停掉。
同一行里它自己认的「真值」还是 681.36 —— 那是闭包捕获的那份过期视图结构体：
`@State`（`running` / `target` / `startDate`）是活的、`let value` 是死的，
两种寿命在同一个闭包里并存。§9.3 那句「结束回调只允许结束它所属的动画」要的就是这个。

现在（`after/03-period-number.log`）只有带轮次号的落定，且**被顶掉的轮次根本不出声**：

```
10:26:51.444  起第3轮 从680.99 到 227.12 目标值就是屏幕上这一格
10:26:52.080  第3轮落定 显示227.12 真值227.12
10:26:53.308  起第7轮 从551.17 到 227.12 …
10:26:53.947  第7轮落定 显示227.12 真值227.12
```

第 2、4、5、6 轮没有落定行（被下一轮接管了），每一轮都从屏幕上那个数起跳
（680.99 / 493.71 / 325.58 / 551.17），落定那一行永远 显示==真值。
落定判断骑在 `TimelineView` 已经在用的那一帧上（`roll.finishIfDue(at:)`），
没有第二个定时器，也就没有「谁的收尾」这个问题。

**没有靠拉长时长凑分数**：把「起第 N 轮」到「第 N 轮落定」相减，现在真正落定过的四轮是
626 / 636 / 639 / 642 ms（中位 637.5），基准那七轮是 632 / 645 / 646 / 649 / 649 / 650 / 651 ms
（中位 649）—— 两边用的是同一个 `0.62` 常量（`Motion.number` / `NumberRoll.duration`），
现在比基准还短约 1.8%。（基准的定时器和动画时长都是 0.62，所以它那七轮的长度本来就不会变，
这一项比的只是「有没有谁偷偷拉长」，答案是都没有。）

一帧的边界也写清楚，免得下一段又拿单帧当稳态：
`build/verification/pr6/frames/before-stale-total-13.1.png` 那一屏头部 ¥232.37、环形 ¥227.12，
看着像「冻住一个错数」，其实是外部快门打在滚动中途的一帧 ——
同一趟日志的最后一行是 `屏幕上=227.12 真值=227.12`，基准的收尾数字是对的。

### 场景 04 · 柱 ↔ 线（§6.1 响应链 + §8.4 图表）

这一场拍到的不是动效差，是**点击根本没上屏**。VFR 录屏里「屏幕没变就不出帧」，
所以「多少毫秒没有新帧」是可以直接数的：

- 基准「切到折线」按下 = 视频 13.096 s。该区域 **11.657 → 14.633 s 一帧都没有**
  （2976 ms 空窗，逐帧时间列上直接断掉），首帧动 +1585 ms（0.15 尺那一步是 14.665，+1569 ms），
  真正走线只有 14.665 → 14.963 这 298 ms / 19 帧。
- 基准「切回柱状」按下 = 16.878 s。15.640 s 之后该区域到录屏结束（18.435 s）**只交出
  18.382 和 18.408 两帧，且两帧 MAD=0.00**（重复帧）—— 这一下到录屏结束都没换画法。
  检测器报的「找不到后续运动」是真的找不到，不是阈值问题。
- 成因在源码里：基准 `SubPreferences.trendChartStyle` 的 setter 只写 UserDefaults 不发布变更，
  视图不重算。这个洞是 PR4 补的，PR6 只是把它量出来。
- 现在：「切到折线」13.542 按下 → 13.645 起首帧动（**+103 ms**），柱子淡出 + 折线逐段走出，
  13.645 → 13.925 共 17 帧（约 280 ms，峰值单帧 MAD 1.89）；
  「切回柱状」17.199 按下 → 17.288 起（**+89 ms**，这一段单帧 MAD 只有 0.2–0.8，
  在突发检测器的 1.0 阈值以下，靠逐帧 dump 才看得见），折线淡出、柱子从短桩长到位，
  17.288 → 17.890 共 36 帧（约 602 ms）。EON 自己这两下是 500 / 500 ms（ev 325/326），
  基准那一下真正走线的 14.665 → 14.963 是 298 ms / 19 帧 —— 三次都算同一把尺：
  相邻帧差 ≥0.15 视为「这一帧在动」，<0.15 算回到静止。

`latency.py` 在这一场把「切回柱状」的首帧动报成了 18.742 s（+1543 ms）—— 那是脚本收尾
重排面板的那一下，不是这次点击的回车。**上面这组数出自逐帧 dump 和接触表**

17.40 / 17.70；`build/verification/pr6/frames/after-chart-second-toggle-strip.png`：

### 目测和测试逼出来的三个真缺口（改的都是生产代码）

1. **「再随机一次」按下去其实没换**。测试先写出来就是红的：`rank` 是 `H(seed ++ id)` 的 FNV-1a，
   而 FNV 是滚动的 —— seed 的影响整体乘在前面，于是 `rank = H_seed · p^36 + f(id)`，换 seed 只是把同一批键
   在数轴上平移一格，**排出来的顺序还是那个顺序转了个圈**。现在哈希末尾补了 splitmix64 那三步雪崩。
   「至少挪 8 个位置」这条断言就是为了拦这个形状：只断言「和上一次不一样」的话，转一圈也能算过。
2. **随机档把置顶的那条洗走了**。这是看 `40-random-after-reshuffle.png` 发现的，不是测试想的：
   那一版把置顶的当普通行参与随机，它掉到了列表中间 —— 而置顶要的就是「不管怎么排都得一眼找到」，
   这个开关等于白设。相对已发布的排序器是**行为回归**，所以 `sorted` 改成四档一律先放置顶、
   其余全体参与当前档；`testRandomKeepsPinnedOnTopWithoutDuplicatingIt` 把这条钉住。
3. **空态那句长提示顶到屏幕两头**（`35-empty-search-no-match.png`：把关键词整段念出来的那一句）。
   补了 `.padding(.horizontal, SauryTheme.screen)`。

另外两条也是这一段改的生产代码，一并记在这儿，免得只看见截图看不见口径：

2. **图标库里有按得动、却什么都选不出来的格子**。`newsletters.fill` 这类 SF 符号名字跟着系统版本走，
   在这台系统上 `Image(systemName:)` 什么都不画：格子上是个空方块，点下去订阅卡片也跟着空掉，

## PR2c · 导入预览与逐行纠错

### 已自动测试（155 项全绿，其中导入相关 47 项）

`SauryTests/ImportParserTests`（21）+ `SauryTests/ImportConflictTests`（26）覆盖：

- 解析层：引号内逗号与换行、BOM、制表符/分号分隔、无表头按列位、表头别名、
  GBK 等单字节旧编码明确拒绝而不是读成乱码、UTF-16、空文件与坏文件报具体原因。
- 字段级：`failedFields` 精确指出哪一列没读出来（金额、周期、币种、日期各自独立），
  改好一列后那一列就从 `failedFields` 里消失。
- 冲突层：稳定 UUID 优先于名字；名字相同内容不同 → 默认跳过并列出差异；
  内容一致 → 默认不重复导；文件内部自己撞车（同编号 / 同内容 / 两行改同一条）→ 第二条默认跳过。
- 预览状态机：`reresolve` 只留住「用户真点过、且当前状态还允许」的选择；
  编号撞上时不给「新建」这条假路径；分区不重不漏；全选只覆盖能导的行；
  `willChangeLocalValues` 只在「按名字对上且确有数字差异」时为真 —— 也就是确认弹窗的触发条件。
